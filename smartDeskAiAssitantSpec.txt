SmartDeskAiAssistant chatbot called Moxa at Synergy.Inc
========================================================

1 SmartDeskAiAssistant chatbot called Moxa replies HR and IT related questions for employees at Synergy.Inc. On a high level it has following capabilities:
1.1 Knowledge-Base Query (RAG): The employee asks a question. The agent searches a vector store built from company IT and HR documents. If a confident answer is found, the agent responds directly.
1.2 Ticket Creation (Write Operation): If the agent cannot find the answer, it offers to create a Jira support ticket. Before creating the ticket, it must collect the employee’s email address.
1.3 Ticket Status Check (Read Operation): An employee can ask “What is the status of my ticket?” The agent retrieves Jira ticket and reports back.


2 Knowledge Base (RAG Pipeline)
2.1 Use the two knowledgebases provided in the data folder namely, hr_kb.json and it_kb.json as input to RAG
2.2 Indexing and Retrieval
Build two separate RAG pipelines (for hr and it each) that ingest the documents and makes them searchable. The pipeline has dense and sparse retrieval strategies.
Dense vector search uses OpenAI embeddings, Qdrant vector DB and Sparse keyword search uses BM25, Qdrant vector DB. Hybrid search combines dense and sparse retrieval with a re-ranker.
The retrieval pipeline returns relevant chunks for a given query, and that the LLM uses these chunks to generate a grounded answer. The agent MUST NOT hallucinate answers that are not present in the knowledge base.
2.3 Confidence Handling and Escalation Logic
HR and IT agent must be able to determine when it does not know the answer. There is no single correct way to do this. 
Below are some approaches you might consider (you may use any other method):
Retrieval-score threshold: If the top retrieved chunk has a similarity score below a certain threshold, treat the query as unanswerable.
LLM self-assessment: Instruct the LLM via its system prompt to explicitly say “I don’t have enough information” when the retrieved context is insufficient.
No-retrieval fallback: If zero chunks are returned, default to escalation.
A combination of the above with a human-in-the-loop confirmation before escalating. When the agent determines it cannot answer, it must transition to the Ticket Creation flow


3. Ticket Creation (Write Operation)
3.1 When the agent cannot resolve a query from the knowledge base, it must offer to create a support ticket using Jira. 
Before the agent creates a ticket, it must collect at minimum the following information:
Employee Email: Mandatory. A unique identifier to link the ticket to the employee. The agent should ask for this explicitly if not already known.
Issue Summary: Mandatory. A short, one-line title for the ticket (e.g., "Unable to connect to VPN from home").
Issue Description: Mandatory. A detailed description. The agent should summarise the conversation so far. The employee should be able to add more details.
Label: Auto generated by the agent. HR by hr_agent and IT by it_agent
Priority: Optional. Low, Medium, High, or Critical. The agent may infer this or ask the employee
3.2 Human-in-the-Loop Confirmation
Before submitting the ticket, the agent must present a summary to the employee and ask for explicit confirmation. 
For example: “Here is the ticket I will create for you: [summary]. Shall I go ahead?” 
This is a mandatory requirement — the agent must not create tickets silently.
3.3 Post-Creation Feedback
After the ticket is successfully created, the agent must confirm this to the employee and provide the ticket ID or a link so that the employee can track it independently.

4 Ticket Status Check (Read Operation)
An employee must be able to ask the agent about the status of a previously raised ticket. The flow is:
The employee asks something like “What is the status of my ticket?” or “Did anyone look at my VPN issue?”
The agent asks for the employee’s email address (if not already known in the current session) to look up their tickets.
The agent queries Jira using the API to fetch tickets associated with that email.
The agent presents the status (e.g., Open, In Progress, Resolved, Closed) along with any comments or updates from the support team.
If the employee has multiple open tickets, the agent should list them briefly and let the employee choose which one they want details on. 
If no tickets are found, the agent should say so clearly.

5. Non-Functional Requirements
5.1 Conversation Quality
The agent must maintain a polite, professional, and empathetic tone throughout.
The agent must handle greetings, small talk, and out-of-scope questions gracefully.
The agent must not hallucinate. If the KB does not contain the answer, the agent must acknowledge it.
5.2 Session & Context Management
The agent should remember context within a single session (e.g., do not re-ask for email).
Multi-turn conversations must flow naturally without losing track of the topic.
5.3 Error Handling
If the external API is unreachable, the agent must inform the employee politely and suggest trying again later.
If the LLM API call fails, the agent should have a retry mechanism or a graceful fallback.
All API keys and secrets must be stored in environment variables — never hard-coded.

9. Step-by-Step Implementation Guide
Follow these phases in order. Each phase builds on the previous one and produces a testable milestone.

Phase 1: Project Setup & Config
Goal: Get LLM responding, and a basic graph compiling.
The skeleton project folder structure is already created
Existing pyproject.toml has project metadata, dependencies, and [project.scripts] entry
config.py: load OPENAI_API_KEY from environment, initialize ChatOpenAI (gpt-4o) and OpenAIEmbeddings
logger.py with a setup_logger() function using Python's logging module
Add state.py with a SmartDeskAiAssistant TypedDict containing: messages, user_query, route, hr_response, it_response, final_answer


Phase 2: Data & RAG
Goal: Build the hr and it vector store and verify hybrid search works.
Use in hr_kb in data folder for hr RAG pipeline with hybrid search 
Use in it_kb in data folder for it RAG pipeline with hybrid search
Build tools/rag.py build hr and it hybrid search RAG and expose both retriever
Build tools/hr_tools.py: create a @tool function search_menu_catalog that uses the retriever
Build tools/it_tools.py: create a @tool function get_order_status that searches by order ID, tracking ID, or email
Verify: import the tools and test them directly with sample inputs

Phase 3: Jira Ticket creation and read workflow
Goal: Build Jira tools for creating and searching tickets
Verify: import the tools and test them directly with sample inputs

Phase 4: Generate multiple agents:
Goal: 
Build each agent as a standalone node function that can be tested independently.
Build orchestrator agent: decides if user query is related HR or IT and routes to the appropriate agents: hr_agent or it_agent.Use llm.with_structured_output() with a Pydantic model that returns a list of agent names + reasoning
Build hr agent: handles HR query using hr knowledgebase using HR RAG pipeline. It also handles general questions not related to HR or IT, greetings etc
Build it agent: handles HR query using it knowledgebase using IT RAG pipeline.
Build synthesizer_agent: synthesize response from both sub agents hr_agent and it_agent and present user with a coherent response
Write system prompts in agents/prompts.py for: Orchestrator, HR Agent, IT Agent,Synthesizer
In addition, add appropriate tools agent.

Phase 5: Graph Assembly
Goal: Wire everything into a working LangGraph StateGraph.
Create a StateGraph, add all nodes, add edges (START -> orchestrator, final node -> END). The orchestrator uses Command + Send() to dispatch to agents in parallel. 
Compile with MemorySaver checkpointer for multi-turn conversation memory
Verify: invoke the graph with a test query and check the final_answer in the result

Phase 6: CLI and Human in the loop
Goal: Build the interactive text loop with interrupt handling.
In main.py: create a SmartDeskAiAssistant class that wraps the compiled graph
Implement the ask() method: invoke the graph, then check graph.get_state() for pending interrupts
For each interrupt: show the question via input(), collect the answer, resume with Command(resume=answer)
Build run_text_loop(): a REPL that reads input, calls ask(), and logs the response
Add quit command
